# 13 - Review marks: per-photo / per-board approve, reject, rework (2026-11-24)

Reviewers (Recce Operations = stage `OPS`, Client Servicing = stage `CS`) can now answer on **each photo and each board detail**, not only on the whole shop. Remarks are mandatory, every change is kept, and the other team can see what was decided.

## What a reviewer can do

On the web review workspace (`/recce-review/<id>`, default view **Boards**):

- Every board of the version is a card: `Board 1 - GSB-01`, Qty / Width / Height, a chevron to open or close it.
- Inside: **Board details** (Media type, Quantity, Size, each with a checkbox) and **Angle Photos** (every photo above its own checkbox, responsive 2 / 3 / 4 columns). "Select all photos" is one click.
- **Action for Selected (n)**: Approve / Reject / Request Rework, with the **Rejection / Rework Reason** box (counter 0 / 500). Reject and Rework need a remark of 3+ characters (the button shows an error, the server answers 422). Approve needs none.
- Each tile shows what **both stages** said: `Ops: Approved` `CS: Rework`, and the reason under it. The ring marks your own stage. So the Operations login sees the Client Servicing answer and the other way round.
- **History** under every board: every mark of every version, including earlier answers (Approved -> Rejected -> Approved), with reason, who and when.
- A reviewer can change a mark at any time while the version is with the review teams, also after the stage approved (Approved -> Rejected / Rework). The right panel then shows **Marked for the recce person (n)** with an "Approve instead" button per item, and **Send n items back for rework**. Approve is blocked while items are marked.
- The older "Photo viewer" view (big photo, zoom, compare with the previous version, Reject photo) is still there; Reject photo there also writes a mark.

## Rules (backend)

- Model: `RecceSubmission.marks[]` (embedded, same document as photos / versions / reviews / reworks). One entry per **(version, stage, thing)**; thing = a photo, or a board field `MEDIA_TYPE | QUANTITY | SIZE`. `decision` = `APPROVED | REJECTED | REWORK`, `reason`, `reviewer`, `at`, `sent`, `history[]` (earlier answers with their reasons).
- `POST /recce-review/submissions/:id/marks` `{ stage, versionNo, decision, reason, targets: [{kind:'PHOTO', photo} | {kind:'BOARD', mediaKey, field}] }`.
  - 403 if the caller is not that stage (Admin / Management cannot mark), 409 if the version is not current, the stage already sent its decision, or it is not that stage's turn (sequential mode only), 400 for a photo / board that is not in the version, 422 for a missing or too short remark.
  - Each write is one atomic update (compare-and-set on the single mark, or push guarded by "no such mark"). The two stages never block each other.
- Sending Rework (`/decision` with `REWORK` or `ADDITIONAL`, or `/change-decision`) adds the stage's unsent `REJECTED / REWORK` marks as rework items and sets them `sent`: photo -> `REPLACE_PHOTO` (`rejected: true` when marked Rejected, `note` = reason); board field -> `FIX_MEDIA_TYPE`, `FIX_QUANTITY`, `FIX_MEASUREMENT` (size) with `mediaKey` + `note`. Items the caller sent itself are not doubled. Approving (`/decision` `APPROVE`) is refused with 400 while the stage has unsent marks.
- Marks belong to a version. Version 2 starts with no marks; version 1 marks and history stay. After the recce person resubmits, each stage approves / rejects again and that is stored under the new version.
- Workspace payload: `marks[]` (all versions, names resolved, `history[]`), `me.canMark`. **Bug fixed on the way:** in parallel review `me.canDecide` was only true for the first pending stage, so Client Servicing could not decide before Operations; now a stage can decide whenever its own review is `PENDING` (sequential mode unchanged).
- New rework item types: `FIX_QUANTITY`, `FIX_MEDIA_TYPE` (they need no answer to resubmit, like `FIX_MEASUREMENT`). New timeline event `ITEMS_MARKED` (visible to reviewers, not to the field person).

## Phone (recce person)

See the mobile section below: board details and photos that were rejected or sent for rework show with the reviewer's reason; an alert tells the person to retake; the rejected photo and the new photo are shown side by side, and earlier images stay in the revisions strip.

## Known limits

- The other stage's marks that were not sent are not forwarded when the first stage sends Rework (the version closes, the other stage's review becomes `VOID`); they stay in the history as "not sent".
- A photo / board the stage approved as a whole (stage decision `APPROVED`) shows `Approved` on every tile without a mark of its own; only explicit marks carry a reason and history.
- Existing Atlas data needs no migration (`marks` defaults to empty).
